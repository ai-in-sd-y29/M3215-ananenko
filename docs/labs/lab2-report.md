## 1. Цель

Расширить бота Lab 1 до AI-агента: модель выбирает действие, приложение проверяет его и
вызывает через собственный MCP-сервер, результат используется в ответе. Операции с
побочным эффектом защищены подтверждением, доверенным владельцем и идемпотентностью.

## 2. Архитектура

| Роль | Компонент |
|---|---|
| MCP-хост | процесс бота (`python -m app`) |
| MCP-клиент | `app/agent/mcp_client.py` (`MCPToolbox`): stdio, discovery, таймауты, переподключение |
| MCP-сервер | `app/mcp_server/` (`python -m app.mcp_server`), низкоуровневый `mcp.server.lowlevel.Server` |
| Агентный цикл | `app/agent/loop.py`: нативный tool calling OpenRouter, ≤ 2 MCP-вызова |
| Подтверждение | `app/agent/confirmation.py` + `app/services/pending.py` |
| Аудит | `app/services/audit.py`, таблица `agent_audit`, команда `/why` |

Транспорт `stdio`: сервер — дочерний процесс бота, сетевой порт не открывается. Схемы
инструментов описаны один раз в Pydantic-моделях `app/mcp_server/schemas.py`
(`additionalProperties: false`), бот получает их только через `tools/list`.

## 3. Инструменты и ресурс

| Инструмент | Тип | Вход | Выход (`structuredContent`) |
|---|---|---|---|
| `get_weather` | чтение | `city` 1–100 | `status ok/ambiguous/not_found`, место+страна, °C, описание WMO, ветер м/с, время наблюдения+TZ, варианты |
| `get_schedule` | чтение | `date` YYYY-MM-DD | `date, weekday, timezone, lessons[start,end,title,location]` |
| `add_reminder` | изменение | `text` 1–500, `remind_at` ISO 8601 с TZ | `reminder_id, text, remind_at, timezone, created` |
| `schedule://current-week` | ресурс | — | неделя пн–вс в `SCHEDULE_TIMEZONE`, занятия по датам |

Ошибки всех инструментов: `isError: true` и `{"error": {"code", "message"}}`; бот переводит
код в понятное сообщение (`app/agent/errors.py`), технические детали остаются в журнале
с `request_id`.

### Выбор погодного сервиса

Open-Meteo (Geocoding API + Forecast API): бесплатен, не требует ключа (нет секрета для
хранения), возвращает `utc_offset_seconds` и IANA-зону точки, русские названия при
`language=ru`. Таймаут каждого запроса `WEATHER_TIMEOUT_SECONDS`, один повтор только для
таймаута/5xx/сетевой ошибки (операция чтения).

Одноимённые города: учитываются только населённые пункты (`feature_code` PPL*), точное
совпадение имени и уточнение страны/региона через запятую. Пункт выбирается однозначно,
только если по населению он минимум в 100 раз крупнее всех остальных одноимённых
(«Москва» — 10,4 млн против 25 тыс. в Айдахо). Иначе возвращается `ambiguous` с
вариантами (страна + область), и бот просит выбрать: «Париж» (Франция 2,1 млн против
Техаса 25 тыс. — меньше 100×) даёт варианты. Первый результат выдачи молча не выбирается.

## 4. Агентный цикл и проверки

- Модели передаются схемы из discovery и локальная функция `ask_clarification`
  (решение «уточнить»). Ответ без вызова — «ответить». Регулярные выражения не используются.
- Неизвестный инструмент, невалидный JSON, лишние поля, нарушение схемы — отказ до
  MCP-вызова (`jsonschema` по `inputSchema`), сервер повторно валидирует Pydantic-моделью.
- Дата расписания — в пределах ±366 дней; напоминание — TZ задана командой `/timezone`,
  время в будущем, однозначно (DST), не дальше года.
- После получения данных инструмента в этом сообщении модели доступны только
  инструменты чтения: данные с «инструкцией» не могут запустить изменение.
- Результат инструмента передаётся как `role: tool` с пометкой источника и
  «недоверенные данные»; клиент MCP проверяет его по `outputSchema`.
- Лимит: 2 MCP-вызова и 3 обращения к модели; при превышении — сообщение и аудит `limit`.

## 5. Владелец, подтверждение, идемпотентность

**Передача владельца.** Бот при старте генерирует случайный секрет и передаёт его только
своему дочернему серверу через переменную окружения `MCP_OWNER_SECRET`. При подтверждении
бот подписывает HMAC-SHA256 токен `{chat_id, action_id, timezone, exp (2 мин)}` и передаёт
его в `_meta.owner_token` запроса `tools/call`. Модель токен не видит и не формирует;
`chat_id` в аргументах отклоняется схемой. Независимый клиент (MCP Inspector) запускает
свой экземпляр сервера без секрета и получает `owner_missing`/`owner_invalid`.

**Подтверждение.** Подготовленное действие хранится в `pending_actions` (TTL 5 минут) с
нормализованными аргументами и TZ. Кнопки содержат только `action_id`; владелец
проверяется по `callback.from_user.id == chat.id`. Новое подготовленное действие того же
пользователя отменяет прежнее (изменённые текст/время требуют нового подтверждения).

**Защита от повторов.**
- Повтор update: `UNIQUE(source_key)`, `source_key = chat_id:message_id`; обработчик
  до вызова модели находит существующую операцию и повторно показывает её.
- Двойное/конкурентное подтверждение: атомарный
  `UPDATE ... SET status='executing' WHERE status='pending' AND expires_at > NOW()` —
  выигрывает ровно один запрос, остальные получают «уже создаётся»/«уже создано».
- Сетевой повтор MCP-вызова: ключ идемпотентности = `action_id` из подписанного токена,
  `UNIQUE(idempotency_key)` + `INSERT ... ON CONFLICT DO NOTHING` → `created: false`.

Проверено интеграционным тестом на PostgreSQL 16 (`tests/test_lab2_integration.py`):
5 параллельных обработок одного update → 1 операция; 5 параллельных подтверждений → 1
напоминание; повтор MCP-вызова → `created: false`; чужой пользователь → отказ.
