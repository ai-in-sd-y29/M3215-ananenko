## 1. Цель работы и выбранный провайдер модели

**Цель:** освоить интеграцию Telegram-бота с большой языковой моделью, реализовать управляемый контекст диалога по пользователям, режимы работы с отдельными системными инструкциями и проверить влияние параметра `temperature` на ответы.

**Провайдер:** OpenRouter (OpenAI-совместимый HTTP API `chat/completions`).  
**Модель:** `openai/gpt-4o-mini` (в кабинете OpenRouter запросы проксировались через провайдеров Azure / OpenAI).  
**Базовый URL:** `https://openrouter.ai/api/v1`  
**Параметры, общие для эксперимента temperature:** режим `/study`, перед каждым запуском `/reset`, один и тот же пользовательский запрос, без обращения к актуальному интернету.

---

## 2. Схема прохождения сообщения через приложение

```text
Telegram (private text)
  → обработчик команд / чата (aiogram)
  → UserService: режим и temperature из PostgreSQL
  → HistoryService: выборка и обрезка истории
  → системная инструкция активного режима
  → LLMClient (OpenRouter)
  → при успехе: сохранение user/assistant в БД
  → подготовка текста (Markdown→HTML при необходимости)
  → ответ в Telegram (при длине >4096 — несколькими сообщениями)
```

Обработчик не формирует HTTP к модели и не содержит SQL: вызовы изолированы в `app/llm/client.py` и сервисах `app/services/`. Конфигурация и секреты читаются только в `app/config.py`.

---

## 3. Хранение и ограничение контекста

В PostgreSQL две таблицы:

- `user_settings` — `chat_id`, `mode`, `temperature`;
- `dialog_messages` — `chat_id`, `role` (`user`/`assistant`), `content`, порядок по `created_at`/`id`.

История разделяется по `chat_id`. При ошибке LLM сообщение ассистента не сохраняется. При смене режима история очищается; `/reset` очищает только историю текущего чата, сохраняя режим и `temperature`.

Ограничения передаваемой в модель истории задаются конфигурацией:

- `HISTORY_MAX_MESSAGES` (по умолчанию 20);
- `HISTORY_MAX_CHARS` (по умолчанию 12 000) — оценка объёма по числу символов.

Стратегия сокращения: оставляются **новейшие** сообщения, пока хватает лимита сообщений и бюджета символов; под текущий запрос резервируется место (`reserved_chars`), системная инструкция и текущий user-текст всегда передаются отдельно и не выбрасываются стратегией обрезки.

## 4. Три системные инструкции и разбор (R.C.T.F.)

### `/study` — объяснение учебных вопросов по программированию
- **Role:** преподаватель программирования для студентов.  
- **Context:** подготовка к лабораторным/экзаменам; нет интернета.  
- **Task:** объяснять просто, с короткими примерами; не сдавать работу за студента.  
- **Format:** русский язык для Telegram, без GitHub-Markdown; структура «ответ → пояснение → пример»; идентификаторы в коде только на английском.  
- **Дополнительно:** блок Truthfulness против галлюцинаций + few-shot пример отказа на запрос «сиксевен».

### `/translate` — перевод
- **Role:** переводчик учебных текстов.  
- **Context:** пользователь указывает язык и текст.  
- **Task:** перевести; если язык не указан — уточнить.  
- **Format:** только перевод (или короткое уточнение).  
- **Few-shot:** три пары «запрос → ответ» (EN, ES, случай без языка).

### `/exam` — экзаменатор
- **Role:** строгий экзаменатор по теме студента.  
- **Context:** только сообщение и история диалога; не выдумывать внешние факты.  
- **Task:** 3–5 коротких вопросов по теме; на ответы — верно/неверно и кратко почему.  
- **Format:** сначала только нумерованный список вопросов; проверка в 2–4 предложениях.  
- **Пример:** тема «Срезы списков в Python» → три вопроса про `a[1:3]`, `a[:2]`/`a[2:]`, `a[::-1]`.

## 5. Эксперимент: влияние `temperature` (12 запусков)

### Условия
- **Запрос (один для всех запусков):**  
  «Объясни разницу между списком и кортежем в Python: когда что выбирать. Ответ строго в три коротких абзаца: 1) суть различия, 2) один пример списка и кортежа, 3) практическая рекомендация. Без Markdown.»
- **Ожидаемые признаки хорошего ответа (зафиксированы до запусков):**  
  1) три логические части; 2) list — изменяемый, tuple — неизменяемый; 3) пример с english-идентификаторами; 4) без `**` и \`\`\`; 5) без явных фактических ошибок.
- **Модель:** `gpt-4o-mini`; входной размер контекста в успешных замерах кабинета — **468** input tokens (константа при `/reset`).
- Запрос с **772** input tokens в логе OpenRouter **исключён** из таблицы (посторонний/засорённый контекстом вызов, не входит в серию из 12).
- Все 12 целевых запусков имеют **468** input tokens; output — по кабинету OpenRouter.

- При **1.0** ответы ещё более «разговорные» и разной длины (719–887); чаще всплывают побочные тезисы (производительность, безопасность), формат трёх частей в целом держится.

## 6. Сравнение исходной и улучшенной инструкции

Сравнивались два запроса при одном режиме `/study` (файл `test3.txt`).

### Слабый запрос
«Расскажи про декораторы»

**Результат:** определение и пример есть, но нет явной границы объёма, нет блока «типичная ошибка», структура ближе к мини-лекции; признаки успеха заранее не зафиксированы в самом запросе.

### Улучшенный запрос (R.C.T.F.)
Role / Context / Task / Format заданы явно (преподаватель 1 курса; 5–7 предложений; english-идентификаторы; без Markdown; порядок: определение → зачем → пример → ошибка новичков).

**Результат:** ответ короче и собраннее; после примера добавлена типичная ошибка («забыть вызвать исходную функцию в `wrapper`»). Пример кода с english-именами (`my_decorator`, `say_hello`) сохранён.

**Сравнение по заранее названным признакам:** улучшенный запрос лучше соблюдает объём и обязательные блоки формата; слабый даёт больше «свободного» текста без пункта про ошибку новичка. Субъективное «красивее» не использовалось как единственный критерий.

## 7. Автоматические тесты и ручная проверка сценариев

### Автотесты (`python -m pytest -q`)
Ключевые сценарии Lab 1 в `tests/test_lab1.py` (без реального Telegram/LLM):

1. Сообщение уходит в модель с инструкцией активного режима.  
2. Истории двух пользователей не смешиваются.  
3. Сокращение истории при лимите без потери порядка и бюджета под текущий запрос.  
4. Смена режима очищает историю и сохраняет режим.  
5. `/reset` очищает только историю вызывающего.  
6. `/settings` принимает 0.0/0.3/0.7/1.0 и отклоняет некорректные значения.  
7. Ошибка LLM → безопасное пользовательское сообщение.  
8. Ответ >4096 символов разбивается без потери текста.  

Дополнительно: проверка обязательности `OPENROUTER_API_KEY`, конвертация Markdown→HTML.

### Ручные проверки (лог `tests4.txt`, 12.10.2026)

| Сценарий | Результат |

## 8. Известное ограничение / пограничный случай

1. **Галлюцинации:** даже с Truthfulness-блоком модель теоретически может ошибаться; промпт снижает риск, но не даёт формальной гарантии.  
2. **Temperature 1.0** увеличивает шанс нарушить жёсткий формат ответа.  
3. **Токены в UI бота не показываются** — для таблицы использовался кабинет OpenRouter; один посторонний запрос (772 input) пришлось исключить вручную.  
4. Сценарий «запомни кодовое слово» плохо подходит для проверки истории, если политика модели запрещает запоминать секреты.

## 9. Декларация использования AI-инструментов

При разработке использовался AI-ассистент в Cursor (генерация каркаса Lab 1, тестов, правок промптов, черновика отчёта).

**Пример отклонённого/исправленного предложения AI:**  
ассистент первоначально оставлял в примерах кода кириллические идентификаторы (`def приветствие(имя)`). Предложение отклонено: в системные инструкции добавлено требование использовать **только английские** имена функций/переменных/классов, строки и комментарии могут оставаться русскими. Также был ужесточён промпт после случая галлюцинации («язык сиксевен»).

Код и результаты тестов проверены самостоятельно; корректность подтверждается запуском pytest и ручными сценариями в Telegram, а не ответом ассистента.
